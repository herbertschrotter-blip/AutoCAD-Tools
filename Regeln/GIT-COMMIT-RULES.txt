1. COMMIT MESSAGE FORMAT (Hybrid)
================================================================================

EINFACH (< 5 Zeilen geaendert):
------------------------------
[vX.Y.Z] Modul/Lib
Typ: Kurztitel


KOMPLEX (Feature, Multi-File):
------------------------------
[vX.Y.Z] Modul/Lib
Typ: Kurztitel

2-4 Zeilen Kontext (WARUM, nicht WAS)

Dateien:
- Datei1.lsp
- Datei2.lsp


REGELN:
-------
- Version IMMER in [vX.Y.Z] Format
- Modul/Lib-Name NACH Version
- Typ (Feature/Fix/Change/Refactor/Perf/Docs) verwenden
- Kurztitel: max. 50 Zeichen, Englisch
- Body: max. 72 Zeichen pro Zeile
- Leerzeile zwischen Kurztitel und Body
- WARUM beschreiben, nicht WAS (Code zeigt WAS)
- Bei Multi-File: "Dateien:"-Sektion mit Auflistung

VERBINDLICH:
------------
Dieses Format gilt fuer ALLE Commits. Kein Datum-basiertes
Format, kein alternatives Schema. Immer [vX.Y.Z] zuerst.

Refactor:  Code-Umstrukturierung (keine Verhaltensaenderung)

Docs:      Nur Dokumentation (README, Kommentare)

6. VERSIONIERUNG (Semantic Versioning - STRIKT!)
================================================================================

FORMAT:
-------
vMAJOR.MINOR.PATCH

BEISPIEL:
---------
v2.3.1
  |  |  └─ PATCH: Bugfixes
  |  └──── MINOR: Neue Features
  └─────── MAJOR: Breaking Changes


WANN WELCHE VERSION:
--------------------
PATCH (v1.0.0 → v1.0.1):
- Bugfixes
- Kleine Korrekturen
- Performance-Verbesserungen (ohne API-Aenderung)
- Dokumentations-Fixes im Code

MINOR (v1.0.0 → v1.1.0):
- Neue Features
- Neue Befehle
- Neue Funktionen (backward compatible)
- Erweiterte Funktionalitaet
- Logging/Config hinzugefuegt

MAJOR (v1.0.0 → v2.0.0):
- Breaking Changes
- API-Aenderungen
- Entfernte Funktionen/Befehle
- Grundlegende Umstrukturierung
- Namespace-Aenderungen

REGELN:
-------
- Version IMMER erhoehen bei Aenderungen
- NIEMALS gleiche Version fuer verschiedenen Code
- Patch fuer JEDEN Bugfix (auch kleine)
- Minor fuer JEDES neue Feature
- Major nur bei Breaking Changes
- Kein Ueberspringen (v1.0.0 → v1.0.1, NICHT v1.0.0 → v1.0.5)

9. COMMIT-CHECKLISTE
================================================================================

Vor jedem Commit pruefen:

[ ] Version korrekt erhoeht? (PATCH/MINOR/MAJOR)
[ ] Format: [vX.Y.Z] Modul/Lib? (NICHT Datum-Format!)
[ ] Commit-Typ gewaehlt? (Feature/Fix/Change/Refactor/Perf/Docs)
[ ] Kurztitel aussagekraeftig? (max 50 Zeichen, Englisch)
[ ] WARUM beschrieben (bei komplexen Changes)?
[ ] Dateien-Liste vollstaendig (bei Multi-File)?
[ ] Code getestet?
[ ] Keine Debug-Ausgaben im Code? (oder hinter *debug-mode*)
[ ] Log-Meldungen aktuell? (neue Funktionen geloggt?)
[ ] Version im Code-Header aktualisiert?
[ ] Rechtschreibung geprueft?


================================================================================
10. BRANCH-STRATEGIE
================================================================================

MAIN:
-----
- Immer stabil
- Nur getesteter Code
- Alle Commits tagged

DEVELOP (optional):
-------------------
- Entwicklungs-Branch
- Features hier entwickeln
- Merge zu main nach Test

FEATURE-BRANCHES (optional):
----------------------------
- feature/plansatzmanager
- feature/filter-sync
- Merge zu develop nach Fertigstellung

FUER SOLO-PROJEKTE:
------------------
→ Direkt auf main committen ist OK
→ Branches nur fuer grosse Features (z.B. Plansatzmanager)


================================================================================
11. WICHTIGE REGELN - ZUSAMMENFASSUNG
================================================================================

VERBINDLICH:
- Version IMMER in [vX.Y.Z] Format (KEIN alternatives Format!)
- Modul/Lib-Name nach Version angeben
- Typ (Feature/Fix/Change/Refactor/Perf/Docs) verwenden
- WARUM beschreiben, nicht WAS (Code zeigt WAS)
- Bei Multi-File: "Dateien:"-Sektion mit Auflistung
- Kurztitel: max. 50 Zeichen, Englisch
- Body: max. 72 Zeichen pro Zeile
- Leerzeile zwischen Kurztitel und Body
- Semantic Versioning strikt einhalten
- Version im Code-Header UND im Commit muessen uebereinstimmen

CLAUDE-SPEZIFISCH:
- Claude verwendet IMMER das [vX.Y.Z] Format
- Claude schlaegt NIEMALS ein Datum-basiertes Format vor
- Claude prueft ob Version im Code und Commit uebereinstimmen
- Claude erinnert an fehlende Log-Eintraege bei neuen Funktionen
